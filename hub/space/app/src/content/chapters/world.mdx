## How the environment works

One AgentEnv `multi` env over two MCP servers behind the AgentEnv gateway:

| Server | What it holds |
| --- | --- |
| `aws` | AWS Emulator (telemetry off, loopback only); the AWS CLI in process with an action log, fault rules and coarse IAM per profile; the world (endpointd plans and enactors, DNS negative caches, the ledger-writer storm, traffic, the event timeline, scripted colleagues and their approvals); fleet tools (`epctl`, `dig`, `systemctl`, `journalctl` on simulated hosts); the meter; `wait`; the horizon. |
| `workspace` | Chat, tickets, wiki, a read-only code host, mail, pager and a public status page, in memory with full history. Every call is charged through the `aws` meter. |

**Time.** The gateway clock is armed frozen at the task's start, and only the `aws` server moves it. Each charged call
takes the agent lane, advances the world and the gateway clock to its execution time, runs, and lets the world observe
it: action events, colleagues' replies, cancellations of timeline events the call made moot. Between the agent's turns
the harness lets up to ten minutes pass and wakes the agent with whatever arrived. The agent has at most 250 tool calls.

**Physics.** The world ticks every 10 s. Checkout success follows which hosts can resolve the ledger; ledger-writer's
regime (healthy, degraded, collapsed) follows offered load against capacity; the webhook backlog and the checkout outbox
drain or grow with the dispatcher's concurrency and the replay rate the agent can set. The physics is deterministic per
seed, so a scripted path scores the same every time.

**Colleagues.** Scripted characters with jobs and moods: the payments lead who blames the last deploy and wants a
rollback, the rotation incident commander who approves changes outside the runbooks, the endpointd owner on his phone,
a key merchant's CTO who emails. Their lines and the agent's replies are matched by a deterministic classifier, so the
same reply gets the same answer.
