## Methods and caveats

**How the runs were made.** Each run deploys the AwsBench bundle with AgentEnv, arms the gateway clock at the task's
start (02:40 ET for T01, 08:15 ET for T03), and prompts the solver once with the page; a post-turn hook lets up to ten
minutes pass between turns and wakes the agent with what arrived. The solver is Claude Code driving Claude Opus 5.5 or
Claude Sonnet 5.5 through a model endpoint, with its built-in tools off: it acts only through the `aws` and `workspace`
MCP tools. T01's budget is 250 tool calls and the 02:40–05:10 window, graded at 05:10; T03's is 220 calls and the
08:15–13:00 window, with the world then fast-forwarded to the 16:15 horizon and graded there. The judges (T01's C11
handoff, T03's C13 root-cause write-up and C18 public text) are an LLM given a fixed fact list.

**What the viewers read.** `tools/export_run.py` turns each run folder into the viewers' JSON: the agent's calls from
the `aws` server's meter and action log, with arguments and results from the agent's session; the world's series
(checkout, ledger-writer load and capacity, webhook backlog, per-host DNS recovery, the ledger record's state, the
dispatcher's concurrency, endpointd's kill switches); colleagues, pages and emails from the timeline and the workspace
records; and the grader's rows. Which checks a call "bears on" is a heuristic over its tool and arguments, not the
grader's attribution. Everything is scrubbed (keys, internal hosts, local paths and endpoints, foreign IPs, account ids
other than the emulator's) and checked before publishing.

**T03's per-host states.** T03's world export keeps the fleet's host counts per minute, not each host's state, and no
export records a host's threads. So `tools/t03_replay.py` replays each T03 run's own calls (the AWS writes, fleet
commands and restarts in its action log, at the times the meter charged them) through the world package in process,
with in-memory fakes, and samples every host's state, a sample host's threads against its limit and the state of the
scheduled action every 30 s. Each replay is checked against the run's export: its per-minute host counts match the
run's at every minute from 08:15 to 16:15 for every T03 run shown. The stretch from 06:00 to 08:15 is the scenario's
own presimulation, the same in every run.

**The references.** Each task's scripted oracle path from the repository's end-to-end driver, replayed by
`tools/build_hub_data.py` through the world package in process with in-memory AWS and workspace fakes: the same
physics, timeline and colleagues, timed by the same meter, with waits run to their full length. On a deployed env T01's
path grades D12 1.0. T03's outcome checks (C02 to C06, C15, C16) are computed by the grader's own rules on the replayed
world; its process and communication marks are the ones the path is built to pass.

**Caveats.**

- **Development runs.** Runs on older builds met env and grader bugs that the runs themselves found; they are kept for
  what they show, and the final runs will replace them. All T03 runs shown are development runs: the first runs on the
  T03 build, while its known env bugs are being fixed.
- **Builds.** The R8 and T03 run folders' build files were left blank by the run script; the commit shown is the
  branch's head when each run started.
- **One run each.** A single run per model and build is an example, not a rate.
- **Calibration is open.** T01 is meant to sit near a 10–18 % frontier pass rate; on the latest build Opus passed all
  three of its runs and Sonnet one of two, and the levers (the cost of shedding late, the approval process, colleague
  pressure) are being tuned. Three of T03's five first runs pass; the other two recovered the fleet but were capped at
  0.4 by a gate.
- **The judges are noisy.** In T01, C11 decides about six points; in T03, C13 and C18 decide twelve.
